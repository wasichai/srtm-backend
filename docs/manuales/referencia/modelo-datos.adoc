[[ref-modelo-datos]]
== Modelo de datos

El modelo de {sigla} no está en migraciones SQL propias: es metadata de wasichai, declarada en `model/model.json` y
cargada por REST con `model/apply.py`. Core guarda la definición (objetos, campos, relaciones, opciones de las listas,
índices y reglas) en su esquema de metadata y crea, por cada objeto y cada organización, una tabla física de
registros. `model.json` tiene *42 objetos, 44 relaciones y 61 listas de opciones (enums)*.

[[ref-modelo-almacenamiento]]
=== Dónde se guarda

[cols="3,9",options="header"]
|===
|Esquema |Contenido

|`wasichai`
|La metadata y la plataforma, creadas por las migraciones Flyway de wasichai al arrancar: `organizations`, `users`,
`roles`, `user_roles`, `permissions`, `field_permissions`, `custom_objects`, `custom_fields`, `relationships`,
`audit_log`, `user_preferences`, `object_actions`, `service_accounts`, `org_units`, `user_org_units`,
`idempotency_keys` y las tablas de los módulos (`workflows`, `document_types`, `document_counters`, `documents`,
`forms`, `views`, `pages`). Cada módulo lleva su historial de migraciones: `flyway_history_core`,
`flyway_history_core_seed` (solo si corrió la semilla de desarrollo), `flyway_history_workflow`,
`flyway_history_documents`, `flyway_history_views`, `flyway_history_forms`, `flyway_history_pages` y
`flyway_history_gis`.

|`app_data`
|Una tabla por objeto y organización, llamada `<objeto>__<8 primeros hex del id de la organización>` (por ejemplo
`cuota_arbitrio__a1b2c3d4`). Cada tabla tiene `id`, `organization_id`, las columnas de sistema de Core y una
columna por campo; un campo de relación es una columna con el id del destino. Core crea un índice por
`organization_id`, por cada campo único y por los `indexes` que el objeto declara.

|`public`
|Las extensiones: `pgcrypto` (Core), `postgis` (wasichai-gis) y `vector` si el servidor la trae (Core la crea solo
cuando está disponible; nada de {sigla} la usa).
|===

NOTE: {sigla} no tiene migraciones SQL propias. Lo único que escribe directamente en `app_data`, sin pasar por
`RecordService`, son los estados de los trabajos y lotes de la emisión masiva y de la determinación masiva
(`srtm.emision.TablasCore`), con los nombres de tabla y de columna que lee de la metadata de Core.

Consecuencias para la operación:

* Un respaldo útil incluye los dos esquemas, `wasichai` y `app_data`, y las extensiones de `public`: la metadata sin
  las tablas de registros, o al revés, no sirve.
* El nombre físico de una tabla depende del id de la organización. Una consulta SQL directa debe buscarlo en
  `wasichai.custom_objects.physical_table`, no suponerlo.
* Los nombres de columna también los asigna Core (`wasichai.custom_fields.column_name`).

[[ref-modelo-unicidad]]
=== Unicidad, inmutabilidad e índices

Core no tiene unicidad compuesta. Cuando una regla de negocio pide «uno por combinación», el modelo guarda las partes
unidas en un campo `clave` único. Como cada organización tiene su propia tabla, la unicidad es por organización.

[cols="4,8",options="header"]
|===
|Campo único |Forma y garantía

|`cuota_arbitrio.clave`
|`predio\|servicio\|anio\|periodo\|secuencia\|version` (las cuotas anteriores al PU por uso no llevan secuencia). Una
cuota por predio, servicio, año, mes y secuencia de uso; una corrección es otra versión.

|`anulacion_cuota_arbitrio.clave`
|El id de la cuota: una anulación por cuota.

|`codigo_infraccion.clave` / `clave_vigente`
|`familia\|codigo\|vigencia_desde` / `familia\|codigo` mientras la versión rige. Al cerrarse, `clave_vigente` queda
NULL (nunca `""`): PostgreSQL admite muchos NULL en un único, así que hay una sola versión vigente por código.

|`papeleta.clave`
|`familia\|numero`.

|`subsanacion_notificacion.clave`, `anulacion_papeleta.clave`
|El id de la notificación o del acta: una por cosa.

|`resolucion_gerencia.clave_ris` / `clave_descargo`
|El id del acta (una RIS por acta) / el id del descargo (una resolución por descargo).

|`notificacion_resolucion.clave`
|`resolucion\|intento`.

|`movimiento_anuncio.clave` / `referencia_cargo`
|`<anuncio>\|AUTORIZACION`, `\|CESE`, `\|RETIRO`, `\|RENOVACION\|<anio>` / `ANUNCIO-<anuncio>-<anio>`: un ejercicio
se devenga una vez.

|`anuncio.clave_idempotencia`
|La cabecera `Idempotency-Key` del alta.

|`zona_arbitrio_ubicacion.clave`
|`servicio\|tipo_via\|via\|manzana\|numero_inicial\|numero_final\|paridad\|vigencia_desde`.
|===

Un valor único repetido responde *409* (`srtm.Duplicados`, en castellano y sin `errors[].field`), nunca 500.

[[ref-modelo-appendonly]]
==== Objetos que solo se agregan

* *`appendOnly` en Core* (ADR-040 de wasichai): `cuota_arbitrio` y `anulacion_cuota_arbitrio`. Core responde 409 a
  un PUT o DELETE de uno de sus registros, por cualquier vía y para cualquiera, y también al borrar un predio,
  contribuyente, servicio o parámetro al que apunta una cuota. `apply.py --drop` apaga `appendOnly` antes de
  borrarlos.
* *Regla de escritura de {sigla}* (`srtm.GuardiaDeEscritura`): los ocho objetos de infracciones, `anuncio` y
  `movimiento_anuncio` solo se agregan (cambio, borrado o transición: 409) y solo los escribe la API de {sigla}
  (sin la marca `EscrituraDeSrtm`, 403 también a un ADMIN). La única edición permitida es cerrar una versión del CUIS.
  `cuota_arbitrio` también tiene su regla (invariantes al insertar), sin exigir la marca.

[[ref-modelo-indices]]
==== Índices declarados

`cuota_arbitrio` declara `(anio, predio)` y `(anio, contribuyente)` en `indexes`. Core los crea en la tabla de cada
organización, también en una que se cree después. Un año trae de 540 000 a 900 000 cuotas; medido en el CI sobre
505 000 filas, listar un predio pasó de 62 ms a 3,3 ms. Ningún otro objeto declara índices: Core indexa
`organization_id`, el estado y los campos únicos.

=== Geometrías

[cols="4,3,5",options="header"]
|===
|Campo |Tipo y SRID guardado |Notas

|`predio.lote_geom`, `catastro_fiscal.lote_geom`
|POLYGON, EPSG:32718 (UTM 18S)
|La API los recibe y devuelve en GeoJSON EPSG:4326. Un MultiPolygon de una parte se toma como Polygon al importar.

|`brecha_predio.lote_geom`
|POLYGON, EPSG:32718

En los DTO del portal una geometría `null` conserva la guardada: el portal la reemplaza, nunca la borra.
